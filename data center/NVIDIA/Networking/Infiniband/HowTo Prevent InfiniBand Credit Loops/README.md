# How To Prevent InfiniBand Credit Loops
InfiniBand 網路被設計為一種無失真網路（Lossless Network）。當網路發生壅塞時，InfiniBand 的標準做法並非藉由丟棄封包（Drop Packets）來因應，而是除非接收端有足夠的緩衝空間，否則發送端不會發送資料。

## Understanding Credit Loops

### Link-Level Credit

每個 HCA 連接埠與交換器連接埠都會在該鏈路（Link）上的發送端與接收端之間實作一套**信用機制（Credit Mechanism）**。此機制是依據**每個鏈路方向**，以及實體鏈路兩端硬體所支援的每個虛擬通道（Virtual Lane, VL）個別獨立實作的。

透過為每個 VL 配置獨立的多個信用「狀態機（State Machines）」與專屬緩衝區（Buffers），能夠實現以下效果：

* 某一 VL 上的流量**不會干擾**另一個 VL 上的流量。
* 在同一個 VL 內部，單一方向的流量**不會干擾**反方向的流量。

當實體鏈路處於連線運作（Active）狀態時，每個 VL 於各方向上的發送端與接收端會持續進行通訊，讓發送端隨時掌握接收端在該 VL 上剩餘的緩衝區空間。可用空間的大小以「**信用（Credits）**」為單位表示，每一點信用代表特定數量的位元組（Bytes）。若接收端該 VL 的緩衝區已滿，發送端將停止發送資料，直到釋出更多空間（信用）為止。當接收端回報可用信用為零時，便開始對發送端施加「**反壓（Backpressure）**」。

在 HCA 連接埠端，若 InfiniBand 應用程式消耗資料的速度不夠快（例如因為程式碼效能低落、核心崩潰/Kernel Panic 或主機 CPU 負載過重等情況），信用機制可允許相鄰的交換器暫停向該伺服器轉發資料。至於從 HCA 連接埠往外發送的流量，信用機制則可讓資料暫留在主機記憶體中，直到相鄰交換器準備好接收為止。

在網路架構（Fabric）內部，假設交換器 S 的連接埠 P 正受到來自相鄰交換器 N 在虛擬通道 X（VL X）上的反壓，所有預計送往連接埠 P 的封包將會滯留在 VL X 的傳輸佇列中。一旦累積的封包過多，交換器 S 用於 VL X 的接收緩衝區資源將會耗盡。此時，交換器 S 會宣告 VL X 已無可用信用，進而對其所有連接埠上的 VL X 施加反壓。依此方式，架構中單一連接埠所產生的反壓能夠一路在整個網路中向上擴散——必要時甚至會從目的端 HCA 一直蔓延回來源端 HCA。

若產生反壓的根本原因持續未排除，在傳輸佇列中等待過久的封包將會發生逾時並被丟棄。此隊頭逾時（Head of Queue / HOQ Timeout）機制是由子網管理器（Subnet Manager）所配置。採用可靠傳輸服務（Reliable Transport Services）的流量，將由來源端 HCA 自動進行重傳。此逾時丟包機制的設計初衷是為了防止網路發生全線死結（Deadlock），而這也是 **InfiniBand 唯一會刻意主動丟棄封包的情境**。

### 信用循環（Credit Loops）

如同許多其他網路一樣，InfiniBand 不喜歡環路（Loops）。具體而言，它特別排斥鏈路反壓（Link backpressure）可能導致死結情況的**邏輯環路**，這些情況被稱為**信用循環（Credit Loops）**。雖然隊頭（HOQ）計時器會定期清除此類死結，但網路效能會受到嚴重影響。信用循環僅代表潛在的死結可能，這取決於環路上各鏈路的流量；然而，在 InfiniBand 的極高傳輸速率下，只要流量模式吻合，死結就會非常迅速地發生。

下圖展示了一個非常簡單的信用循環範例：

![](https://enterprise-support.nvidia.com/servlet/rtaImage?eid=ka0Vv000000AnOO&feoid=00N8Z000003jPco&refid=0EM8Z000003DSf1)

S1、S2、S3、S4 四台交換器連成環狀拓撲，節點 A 接 S1、B 接 S2、C 接 S3、D 與 E 接 S4

**此範例的設定：**

    * 4 個交換器 ASIC 以環狀拓撲（Ring Topology）相互連接。
    * 一個主機介面卡（HCA）將一台伺服器（節點）連接至各交換器，其中交換器 4（Switch 4）額外連接了另一個 HCA。

**其他假設：**

    * 路徑由 Minhop（最小跳數）路由演算法配置。
    * 所有流量均傳送在同一個虛擬通道（Virtual Lane, VL）上。


**流量模式（Traffic pattern）：**

    * 節點 A 連續向節點 C 發送訊息（A $\to$ C）。
    * 節點 B 連續向節點 D 發送訊息（B $\to$ D）。
    * 節點 C 連續向節點 A 發送訊息（C $\to$ A）。
    * 節點 E 連續向節點 B 發送訊息（E $\to$ B）。

在此流量模式下，每條 IB 線纜皆承載著**兩組資料流**。

**若由於某種原因，節點 D 的應用程式無法接收來自節點 B 的封包：**

    * HCA D 對交換器 4（Switch 4）施加反壓。
    * 交換器 4 對來自交換器 3（Switch 3）的鏈路施加反壓。
    * 交換器 3 對來自交換器 2（Switch 2）的鏈路施加反壓，同時也對 HCA C 施加反壓。
    * 交換器 2 對 HCA B 施加反壓，但由於 $A \to B \to C$ 的資料流，也對來自交換器 1（Switch 1）的鏈路施加反壓。
    * 交換器 1 對來自交換器 4（Switch 4）的鏈路施加反壓，同時也對 HCA D 與 E 施加反壓。


此時，**沒有任何一個 HCA 能夠發送資料**。若節點 D 未及時恢復，交換器中的隊頭（Head of Queue）計時器將逾時，所有封包都會被丟棄。使用可靠傳輸服務（Reliable Transport）的封包將進行重傳。整體而言，延遲與頻寬都將嚴重惡化。

**以下是構成 InfiniBand 信用循環的必要條件：**

* 一個**實體環路（Physical loop）**。
* 一組在路徑之間存在**循環依賴關係**的節點間流量路徑（處於同一個 VL 上）。在前面的圖例中，子網管理器配置的四條路徑具有相互依賴性，只要其中一個目的地停滯且所有路徑的流量足夠高，就會引發死結。

> **注意：** 任何構成循環依賴的路徑都會包含至少三台交換器。前面的圖例展示了四條路徑，每條路徑均包含三台交換器。

### 總結
* **信用循環成因**：
    * **實體環路 + 循環依賴**：拓撲中存在實體環路，且多條流量路徑在同一個虛擬通道（VL）上彼此互相依賴（每條構成依賴的路徑至少橫跨 3 台交換器）。
    * **錯誤的路由算法**：使用如 Minhop 等未防範環路的路由演算法時，容易在環狀架構中產生路徑死結。

* **骨牌式反壓擴散流程（連鎖死結）**：
    1. 單一節點停滯（如節點 D 接收不及，對 S4 施壓）。
    2. 反壓沿著鏈路一路逆向蔓延（$\text{D} \to \text{S4} \to \text{S3} \to \text{S2} \to \text{S1} \to \text{S4}$）。
    3. 反壓繞回原點形成「閉環」，造成全網**所有 HCA 均無法再發送任何資料**。

* **後果與代價**：
    * **HOQ 逾時丟包**：雖然交換器具備 HOQ 計時器防死結機制，逾時後會強制丟棄佇列前端的封包以打破死結，但會觸發端點大量重傳，導致網路延遲暴增、頻寬劇降。

## InfiniBand 架構中的信用循環 (Credit Loops in IB Fabrics)

除了規模最小的實際 IB 架構之外，幾乎所有網路架構中都存在實體環路（Physical loops）。這在環狀（Torus）、網狀（Mesh）和超立方體（Hypercube）等拓撲中表現得更為明顯，但對於標準的「胖樹（Fat Tree）」拓撲來說也是如此。從嚴格的技術定義來看，樹狀拓撲本身不含環路，但 IB 的「樹狀結構」其實包含許多實體環路，除非它們是僅具備單一台 L2（Spine / Core）交換器的雙層結構（又稱 Clos-3），也就是真正的樹狀結構。

下圖展示了一個小型的 Clos-3 架構，其中包含多個由 4 台交換器構成的實體環路（類似於前一張圖的架構），圖中高亮標示了其中一個環路。我們的目標是**防止這些實體環路演變成信用循環**。

![](https://enterprise-support.nvidia.com/servlet/rtaImage?eid=ka0Vv000000AnOO&feoid=00N8Z000003jPco&refid=0EM8Z000003DSf6)


### 總結

* **實體環路普遍存在**：除了只有單一核心交換器的極小型拓撲之外，多數實用級別的 IB 網路（包含 Torus、Mesh、Hypercube 以及標準的 Fat-Tree 架構）在實體層線上都存在環路。

* **Fat-Tree 中的實體環路**：在多台 Spine 交換器（L2）與 Leaf 交換器（L1）互連的 Clos 架構下，任意兩台 L1 交換器與兩台 L2 交換器之間就會自然構成 4 台交換器的封閉實體環路（如圖中黃線所標示）。

* **核心防範目標**：實體環路是多路徑容錯與高頻寬必備的佈線特性，真正的網路設計目標是**透過路由演算法（如 Up/Down、ftree）嚴格約束轉發方向，避免實體環路演變為相互等待緩衝區的邏輯「信用循環（Credit Loops）」**。

## Preventing Credit Loops

儘管包含信用循環的輕負載 IB 結構可以長時間運行而不會出現問題，但最佳實踐是在結構設計中消除信用循環。

消除信用循環最常見的技術包括使用：
* A good physical topology, including good node placement
* Better routing algorithms
* Multiple Virtual Lanes

## 藉由實體拓撲消除環路 (Loop Elimination via Physical Topology)

前述的基本環路範例可透過數種方式避免信用循環。下圖展示了四種做法：

![](https://enterprise-support.nvidia.com/servlet/rtaImage?eid=ka0Vv000000AnOO&feoid=00N8Z000003jPco&refid=0EM8Z000003DSfB)

*(圖示：展示 a、b、c、d 四種拓撲調整方案)*

**各拓撲範例說明（a 到 d）：**

1. **方案 a**：移除交換器之間的連線，例如位於交換器 S2 與 S3 之間的連線，以此打破實體環路，因此不可能產生信用循環。
    * 為什麼能解決：環路直接從物理上被破壞（變成一條 C 字形的長鏈：S3 - S4 - S1 - S2）。   
    * 既然沒有封閉的實體圈圈，反壓回傳時走到末端就會停住，不可能繞成一個閉環，自然完全無法形成信用循環。
2. **方案 b**：在對角交換器之間增加一條線纜，例如在交換器 S2 與 S4 之間，這實際上創造了更多實體環路（此例中新增了兩個 3 台交換器的環路）。然而，由於所有 IB 路由演算法皆設計為「最短路徑優先」，此架構中的所有流量皆為僅涉及兩台交換器的「點對點」傳輸。完全不會有需要經過第三台交換器的資料流。因此即便某台交換器的 VL 緩衝區耗盡，反壓也無法蔓延形成循環死結。
    * 直覺疑問：多拉一條線不是產生了更多三角形環路（S1-S2-S4 和 S2-S3-S4）嗎？
    * 為什麼反而能解決：
        * InfiniBand 的路由機制是最短路徑優先。
        * 以前 A 要去 C、或 B 要去 D，必須繞著外圍走 3 台交換器；現在中間有了高速捷徑：
            * B 去 D 直接走：S2 $\to$ S4（只需經過 2 台交換器）。
            * A 去 C 直接走：S1 $\to$ S4 $\to$ S3 或 S1 $\to$ S2 $\to$ S3。
        * 關鍵在於：所有的傳輸都變成了點對點或 2 台交換器以內的短傳輸，完全沒有任何需要跨 3 台交換器的長路徑。
        * 沒有 3-交換器路徑，就無法構成路徑間的環狀互鎖，死結條件被直接打破。   

3. **方案 c**：移除某台交換器上的所有節點（此例中為 S2），藉此消除了經過交換器 S1 與 S3 的 3-Switch 路徑。節點 B 從 S2 移至 S3。在此設計中，3-Switch 路徑會經過 S2（例如 A $\leftrightarrow$ B 或 C 的流量）以及經過 S4（A $\leftrightarrow$ B 或 C 的替代路徑）。然而，由於最短路徑優先路由機制，子網管理器不會配置經過 S1 或 S3 的 3-Switch 路徑（或 4-Switch 路徑）。
    * 為什麼能解決：
        * 原本死結需要 4 條在環上彼此推擠的長路徑（A 到 C、B 到 D、C 到 A、E 到 B）。
        * 當 S2 上面沒有接任何發送或接收主機時，子網管理器（OpenSM）就不需要為 S2 配置那麼多終端進出路徑。
        * 傳輸路徑大幅簡化，無法在環狀拓撲的四個邊上同時湊齊相互牽制的封閉依賴鏈。  

4. **方案 d**：實體拓撲維持不變，改用 **Up/Down 路由** 取代 Minhop 路由演算法。其中一台交換器（此例為 S1）被定義為根交換器（Root Switch）。使用 Up/Down 演算法可禁止 S2 $\to$ S3 $\to$ S4 以及 S4 $\to$ S3 $\to$ S2 的路徑，藉此打破邏輯環路。更多資訊，請參閱[Understanding Up/Down InfiniBand Routing Algorithm](https://enterprise-support.nvidia.com/s/article/understanding-up-down-infiniband-routing-algorithm)。
    * 為什麼能解決：
        * Minhop 演算法只看哪裡最近就往哪裡送，容易讓封包在環上轉圈。
        * Up/Down 演算法制定了一套單向交通規則：
            * 封包「只能先往上爬到 Root（Up），再往下走到目的地（Down）」。
            * 嚴格禁止「先下後上（Down-to-Up）」或在同層橫向亂轉。
        * 因為 S1 是頂點，封包不允許在底部（如 S2 $\to$ S3 $\to$ S4）隨意繞行，這在邏輯路徑上直接砍斷了逆流與轉圈的可能，從根本上杜絕死結。   

在所有這些情況中，信用循環可透過以下方式預防：

* **消除實體環路**；或
* **包含足夠且不超過限制的 3 台以上交換器路徑**，使依賴環路無法成形。

### 實務應用：雙層（Clos-3）架構

此方法在雙層（Clos-3）架構中的實務最佳實踐是：**切勿將伺服器直接連接至 L2 交換器**。

下圖展示了一個存在信用循環的 Clos-3 範例。請注意，**只要移除節點 X 與 Y，就能打破所有環路**：

![](https://enterprise-support.nvidia.com/servlet/rtaImage?eid=ka0Vv000000AnOO&feoid=00N8Z000003jPco&refid=0EM8Z000003DSfG)

*(圖示：L2 交換器接有節點 X、Y，下方 L1 交換器接有節點 A、D、G 等)*


如果在 L2 接了伺服器 X 與 Y 會發生什麼事？
    * L2 原本是純粹轉發的「核心/根節點」，一旦接了伺服器，它就變成了流量的起點與終點。
    * 伺服器 X（在 L2）要送給 A（在 L1），同時 A 又要送給 Y（在 L2）。
    * 這種跨層主機間的流量，會讓封包在 L1 與 L2 之間反覆「上上下下」，破壞了單向 Up/Down 規則，實體環路瞬間轉變成信用循環死結。
    * 因此，把 X 和 Y 移到底層 L1，架構就立刻恢復無死結狀態。 

> **注意：** 位於 Clos-3 架構 L2 層的 **IB 閘道器（IB Gateways）屬於例外情況**，因為它們彼此之間交換的流量極小，不足以形成完整的反壓閉環。其他彼此之間不大量交換資料的節點也可以部署在 L2，即使它們與 L1 節點之間的連線具備高頻寬亦同（另請參閱 [VPI Gateway Considerations](https://enterprise-support.nvidia.com/s/article/vpi-gateway-considerations)）。
> 


### 總結

* **破除信用循環的 4 種拓撲策略**：
    * **斷開連線（方案 a）**：直接移除 S2-S3 連線，從實體上徹底消滅環路。
    * **對角加線（方案 b）**：增加 S2-S4 鏈路，利用最短路徑優先演算法，使所有流量跳數縮減為 2 台交換器以內，避免路徑跨越 3 台交換器而形成循環依賴。
    * **集中節點位置（方案 c）**：將 S2 上的伺服器移至 S3，避免 SM 配置跨 S1/S3 的長路徑。
    * **改用 Up/Down 路由（方案 d）**：不改動硬體線路，指定 S1 為 Root 節點，軟體層面禁止 Down-to-Up 轉發，直接打破邏輯環路。

* **Clos-3 (Fat-Tree) 的黃金建置準則**：
    * **伺服器嚴禁接在 L2（Spine / Core）層**：若伺服器（如圖中的 X、Y）接在 L2，會形成 L2 $\leftrightarrow$ L1 之間的跨層封閉依賴，引發信用循環死結。移除 L2 上的伺服器即可確保架構無死結。

* **唯一例外（Gateways）**：只有彼此之間不互傳內部流量的節點（例如對外的 IB/以太網閘道器），才允許掛載在 L2 交換器上。

## 藉由路由演算法消除環路 (Loop Elimination by Using Routing Algorithms)

有三種常見的 InfiniBand 路由演算法可以使用：

* **最小跳數（Minimum hop, minhop）**
* **Up/Down（updn）**
* **胖樹（Fat tree, ftree）**


> **注意：** 其他路由演算法較不常見，不在本文討論範圍內。
> 
> 

**Minhop** 並**無法消除信用循環**。如同所有的 IB 路由引擎，它以最短路徑生成樹（Shortest-path spanning tree）為基礎，並嘗試在所有可用的實體鏈路上靜態平衡所有節點配對之間的可能邏輯路徑。它會將所有可連通的節點完全互連。因此，當實體網路初次建置上線、正在進行拓撲變更，或是因鏈路或交換器故障而處於降級狀態時，Minhop 是一個很好的預設演算法。對於設計妥當的 Clos-3 網路（具備兩層交換器 ASIC），由於實體連線本身已消除了信用循環，Minhop 確實是可用於生產叢集的簡便選擇，但它**無法應用於超越 Clos-3 規模的網路**。


**Up/Down** 演算法常被用於較大規模的叢集，原因如下：

    * 它**保證絕不會產生信用循環**。
    * 對於非傳統「胖樹」的拓撲結構具備相當良好的容忍度，例如將先前各自獨立的 IB 叢集進行合併時。
    * 建議搭配使用「路由鏈（Routing chain）」功能，為合併後的各個 IB 叢集提供最佳化路由。



若使用 Up/Down 演算法，必須使用一個小型 SM 設定文字檔來定義網路架構中的「根（Root）」交換器。由於該演算法為了破除環路而禁止了某些邏輯路徑，除非嚴格遵循 Up/Down 演算法的最佳實踐原則，否則某些節點之間可能會出現無法互相「ping」通的情況。關於 Up/Down 路由的運作細節與架構設計最佳實踐，請參閱[Understanding Up/Down InfiniBand Routing Algorithm](https://enterprise-support.nvidia.com/s/article/understanding-up-down-infiniband-routing-algorithm)。


**Fat Tree** 路由是 Up/Down 路由的衍生演算法。與 Up/Down 類似，它同樣接受根交換器清單，並保證產生無環路的邏輯拓撲。然而，Fat Tree **僅能對對稱（純）以及接近對稱的胖樹拓撲進行路由**，因此不適用於更具彈性或非標準的樹狀架構。藉由專注在近乎純粹的胖樹架構，Fat Tree 演算法能夠在邏輯路徑上進行**更全面的全域負載平衡**。相較於 Up/Down 的局部平衡，Fat Tree 能提供更高效率的路由。

> **注意：** Up/Down 與 Fat Tree 演算法皆可在未提供根交換器清單的情況下嘗試運作。但不建議在沒有根清單的情況下執行 Up/Down，因為無法保證能夠正確自動偵測出根交換器。Fat Tree 僅在理論上的純胖樹拓撲中才能在沒有根清單時正常運作，否則將會執行失敗。當 Fat Tree 演算法明確獲知根節點時，它能放寬對可路由拓撲的嚴格限制。
> 


### 總結

* **三大演算法定位與特性**：
    * **Minhop**：只負責連通所有節點與做基本路徑平衡，**完全沒有防死結能力**。僅適用於開網初期的臨時除錯，或是規格極為標準且伺服器全在底層的雙層 Clos-3 架構，絕不能用於三層或更複雜的拓撲。
    * **Up/Down**：通用型防死結演算法，嚴格依照上下行規則打破環路。容忍度高、能相容非典型胖樹或拼接的多個叢集，但需要手動指定 Root 交換器，且因封閉部分路徑，平衡能力偏向局部性。
    * **Fat Tree (ftree)**：專為對稱型胖樹量身打造的最佳演算法。同樣保證無信用循環，且能做到「全域負載平衡（Global Balancing）」，傳輸效能與負載均勻度皆優於 Up/Down。

* **Root Switch 清單配置規則**：
    * **不可依賴自動偵測**：雖然軟體具備自動探索能力，但未指定 Root 清單時，Up/Down 容易判定錯誤，Fat Tree 也僅能在完美對稱拓撲下存活。
    * **生產環境最佳實踐**：強烈建議在設定檔中明確提供 Root 交換器的 GUID 清單，以確保拓撲正確辨識並避免節點失聯。
