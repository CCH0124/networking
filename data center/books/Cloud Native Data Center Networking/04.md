# Network Operating System Choices

## Requirements of a Network Device

原生 NOS 的核心需求：

**四大核心需求**：

    1. **設備可程式化性 (Programmability of the Device)**：支援自動化配置（Configuration）與監控（Monitoring），降低維運負擔。
    2. **執行第三方應用程式的能力 (Ability to Run Third-Party Applications)**：可在 NOS 上直接執行 Python 腳本、第三方 Monitoring/Config Agents 或 Container 化應用。
    3. **可替換廠商組件 (Ability to Replace Vendor-Supplied Components)**：允許以開源路由套件（如 FRR）替換廠商自研的路由套件，破除底層網路創新壁壘。
    4. **維運人員可修復 Bug (Ability for the Operator to Fix Bugs)**：擺脫傳統廠商漫長修錯週期的限制，使網路設備具備**伺服器平台 (Server Platform)** 的特性。

* SDN Model of the Network 圖展現控制平面集中於遠端 Controller，具備全網鳥瞰視角（God's-eye view），負責統一調度與發送流表指令。
* OpenFlow and SDN 展示硬體交換晶片簡化為純粹依據流表（Flow Tables / Access Control List 匹配條目）執行轉發/丟棄/改寫（Match-plus-Action）的資料平面設備

2. OpenFlow 在資料中心失敗的病理分析 (Section: The Trouble with OpenFlow)

* 不支援 ECMP：早期 OpenFlow 1.0 的單一流表抽象無法有效處理資料中心 Clos 拓撲的核心——等價多路徑路由（ECMP）
* 流表快取與 Control Plane 瓶頸：將每個新 Flow 的首個封包送往 Central Controller 處理的模式無法擴展，控制平面容易癱瘓
* 硬體流表成本高昂：ASIC 晶片的可程式化 Flow Table (TCAM) 成本遠高於傳統路由/橋接表，且規模無法擴大
* 抽象混淆：OpenFlow 將「配置/統計的可程式化性」與「底層轉發抽象」混為一談，反而創造了新的 Vendor Lock-in（不同 Controller 的流表邏輯不相容）

3. Open Virtual Switch (OVS) 與 OVSDB (Section: OVS)

* OVS：Linux 上最成功的 OpenFlow/SDN 開源實作，運作於使用者空間（`ovs-vswitchd`），重構了 ARP/IP/MPLS 等邏輯
* OpenFlow Controller 透過 OVSDB (RFC 7047) 進行 OVS 交換器配置與狀態查詢，並透過 OpenFlow 協定對 `ovs-vswitchd` 下發流表，廣泛應用於 VMware NSX 與 OpenStack 虛擬化環境

## NOS 架構設計模型 (NOS Design Models)

1. 共通基礎組件 (Common Elements)
    * **底層 OS**：幾乎全網統一採用 **Linux Kernel**（僅 Juniper 傳統 Junos 採 FreeBSD，其新一代 Junos OS Evolved 亦轉向 Linux）
    * **CPU 架構**：高階交換器採低功耗 **Intel x86**，低階/管理設備採 **ARM**

    ```text
    +-------------------------------------------------------------------------+
    |                                                                         |
    |            |||||              .-----.                                   |
    |         +--|||||--+           |  P  |             .-------.             |
    |       ==| +-----+ |===========|  C  |=============|       |             |
    |       ==| | CPU | |           |  I  |             |  SSD  |             |
    |       ==| +-----+ |           |  e  |             '-------'             |
    |         +---------+           |     |                                   |
    |            |||||              |  B  |             |||||||||             |
    |                               |  u  |          +--|||||||||--+          |
    |    Management                 |  s  |        ==| +---------+ |==        |
    |    Ethernet NIC --------------|     |==========| |Switching| |==        |
    |                               '-----'        ==| | Silicon | |==        |
    |                                                | +---------+ |==        |
    |                                                +-------------+          |
    |                                                   |||||||||             |
    |                                                   |||||||||             |
    +---------------------------------------------------|-------|-------------+
                                                        Switch Ports
    ```

    圖中呈現 CPU Complex（CPU、RAM、Storage、OOB 網口）透過 PCI Express (PCIe) 總線與主交換晶片 (Packet-Switching Silicon) 相連。PCIe 匯流排頻寬僅約 **400 Mbps 至 100 Gbps**，而交換晶片吞吐量高達 **3.2 Tbps (32x100GbE)**。因此 **NOS 絕不在主資料轉發路徑上**，NOS CPU 僅處理極少數控制封包（約 150k pps vs 晶片處理超過 5B pps）

2. 核心維度一：網絡狀態存放位置 (Location of Switch Network State)
    NOS 之間最本質的差異，在於「全網轉發狀態的最終真實來源 (Ultimate Source of Truth)」儲存於何處:
    * **特定廠商使用者空間模型 (Vendor-Specific User Space Model)**：
        * 網路狀態僅儲存於 Vendor 於 User Space 的私有 Blob 中，Linux Kernel 對轉發一無所知。代表：Cisco NX-OS、DPDK-based NOS
    * **混合模型 (Hybrid Model)**：
        * 終真實來源仍為 Vendor 的 User Space 數據庫，但部分狀態（如 IP 路由、IP Neighbor）會**同步**至 Linux Kernel，允許部分依賴 Kernel 的第三方應用讀取。代表：Arista EOS、Microsoft SONiC、Dell OpenSwitch。
    * 完全 Kernel 模型 (Complete Kernel Model):
        *　**以 Linux Kernel 的資料結構作為全網狀態的唯一真實來源**。控制協定（如 FRR）直接透過 Netlink 寫入 Kernel，再同步至硬體晶片。代表：Cumulus Linux。

3. 核心維度二：交換晶片驅動與寫入機制 (Programming the Switching Silicon)

    *　圖中繪製出兩種 User-space 晶片驅動取得轉發狀態的管道
        1. **Vendor User Space**：Vendor Stack 直接向 User-space Driver 下發狀態（User Space 模式）
        2. **Linux Kernel / Netlink**：User-space Driver 打開一個 **Netlink Socket (AF_NETLINK)**，作為發布/訂閱 (Publish-Subscribe) 匯流排，監聽 Kernel 網路狀態的變動並寫入硬體

    * 晶片抽象層 (HAL / SAI vs. Switchdev)
        * **SAI (Switch Abstraction Interface)**：由 Microsoft/Dell 發起並貢獻至 OCP，提供標準、獨立於 NOS 的 User-space 晶片硬體抽象層（Azure 強制要求的標準）
        * **Switchdev**：由 Cumulus 與 Mellanox 推進的 **Linux Kernel 內核驅動模型**。將交換晶片埠映射為 Kernel 的 `netdev`，讓標準 Linux 網路指令（如 `ip`、`ethtool`）能直接利用 Hook 卸載（Offload）至硬體晶片

## 使用者介面 (User Interface)

* **非模式化指令 (Non-Modal CLI)**：Linux 指令為可腳本化的非模式指令；傳統網路 CLI 則為模式化 (Modal) 指令（需輸入 `configure` -> `router bgp`）。
* **統一 CLI 趨勢**：Linux 平台上存在多種 CLI，**FRR (Free Range Routing)** 提供了傳統網路工程師熟悉的 Cisco-like CLI，正逐漸成為純路由網路的統一開源 CLI 標準。

* **流程 (a) Packet Send Model（封包發送模型）**：
* **步驟 1**：使用者空間程式（如 `ping`）透過原生 Linux 核心 API 送出封包，進入核心網路堆疊（Kernel Network Stack）。
* **步驟 2**：核心將封包導向由 NOS 廠商建立的虛擬介面（Tun/Tap Interfaces）。
* **步驟 3**：執行於使用者空間的晶片驅動程式（NOS Vendor User Space Stack）從 Tun/Tap 讀出封包。
* **步驟 4**：驅動程式將封包注入硬體交換晶片（Switch Silicon），最終由前方面板連接埠（Front Panel Ports）發送出去。


* **流程 (b) Packet Receive Flow（封包接收流程）**：
* **步驟 5**：交換晶片收到 CPU 相關的例外封包後，直接向上繞送給使用者空間的晶片驅動程式。
* **步驟 6**：驅動程式將該封包寫入對應的 Tun/Tap 介面。
* **步驟 7**：封包由 Tun/Tap 進入 Linux 核心網路堆疊進行解析。
* **步驟 8**：核心網路堆疊將資料遞送給目的應用程式（如 `ping`）。

**Tun/Tap / Hybrid 模型**：Kernel 查表後將封包發往虛擬 `/dev/tapN` 介面，封包彈回 (Boomerang) 至 Vendor 位於 User Space 的網路堆疊，再由 Vendor 專有驅動寫入交換晶片發出。回包時亦需經由 Tun/Tap 在 User Space 與 Kernel 之間來回穿梭
