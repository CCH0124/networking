# los: Network Topology for a New World

* **拓撲即命運 (Form is Destiny)：** 網路拓撲結構是決定數據中心擴展性、可靠性與自動化能力的最底層基石。
* **Clos 拓撲的由來：** 由 Charles Clos 於 1953 年提出（最初用於電話交換網），現代雲端原生數據中心借鑑其分形（Fractal / Redwood Tree）擴展模型，演變為當前數據中心主流的 **Leaf-Spine（葉脊拓撲）** 架構。

---

## Clos 拓撲的基本架構 (Introducing the Clos Topology)

* **兩層式架構角色分工 (Section: Introducing the Clos Topology)：**
    * **Leaf Switch（葉交換器 / ToR）：** 位於 Rack 頂部，負責連接端點伺服器 (Servers/Endpoints)，並上鏈至所有 Spine 交換器。
    * **Spine Switch（脊交換器）：** 純粹作為 Leaf 交換器之間的互連匯聚節點，**絕對不直接連接任何伺服器或提供其他服務**。
    * **全互連鏈路 (Full Mesh Interconnect)：** 每一台 Leaf 設備都會精準連接至每一台 Spine 設備。
* **Scale-Out（橫向擴展）與 Scale-In 的本質差異：**
    * 傳統 Access-Agg 架構採 **Scale-In** 模式（透過提升中央 Agg機箱 CPU/單機效能）。
    * Clos 架構採 **Scale-Out** 模式（透過增加 Leaf 與伺服器擴充工作負載；透過增加 Spine 橫向擴充 Leaf 間的吞吐頻寬）。
* **對折三階 Clos (Folded 3-Stage Clos)：** 經典 Clos 為三階（Input, Middle, Output），將 Output 階段向後對折至與 Input 相同側後，Middle 階即對應為 Spine，Input/Output 階對應為 Leaf。

## Clos 拓撲的核心特性深度剖析 (A Deeper Dive into the Clos Topology)

### 設備同質化 (Use of Homogeneous Equipment)
* **硬體經濟學革命：** 捨棄昂貴且複雜的傳統大型機箱 (Chassis)，全網統一採用簡單、固定埠數的 1U/2U 盒式交換器 (Fixed-form-factor Switches / White-box)，極大地簡化了設備採購、備料管理 (Sparing) 與維運替換流程。

### 以 L3 路由與 ECMP 為基礎互連模型 (Routing as the Fundamental Interconnect Model)
* **全面淘汰全網生成樹 (STP)：** 內部網路不使用 STP 進行 L2 橋接，改以 **IP 路由 (IP Routing)** 作為核心轉發機制。若需跨 Rack 的 L2 連通，則採 Overlay 技術（如 VXLAN）。
* **ECMP (Equal-Cost Multipath) 多路徑轉發：** Leaf 至任何其他 Leaf 經由任意 Spine 的路徑成本完全相同，利用封包的 5-Tuple 進行 Flow Hashing，將流量均勻分散至所有可用 Spine 鏈路。

### 超額與 Clos 數學推導 (Oversubscription & Clos Math)
* **過載比 / 超賣比 (Oversubscription Ratio) 定義：** 下行鏈路頻寬（面向伺服器）與上行鏈路頻寬（面向 Spine）的比例。
* **重排無阻塞網路 (Rearrangably Nonblocking Network)：** 1:1 的過載比稱為無阻塞網路。即使在 1:1 架構下，由於 Flow Hashing 偶發的碰撞（Elephant/Mice Flows 衝突），實務上屬於「可重排無阻塞」。
* **計算數據證明：兩層式 Clos 拓撲公式** (假設採用 $n$ 埠同速率交換器，且採 1:1 超賣比)：
    * **可連接的最大伺服器總數：**
        $$\text{Max Servers} = \frac{n^2}{2}$$
        * 證明範例 (4 埠交換器)： $4^2 / 2 = 8$ 台伺服器。
        * 證明範例 (64 埠交換器)： $64^2 / 2 = \mathbf{2,048}$ 台伺服器。
        * 證明範例 (128 埠交換器)： $128^2 / 2 = \mathbf{8,192}$ 台伺服器。
    * **完全建構所需的交換器總數：**
        $$\text{Total Switches} = n + \frac{n}{2}$$
        * 證明範例 (64 埠交換器)： 需包含 64 台 Leaf 與 32 台 Spine，共 **96 台交換器**。

### 互連鏈路速率與實務物理限制 (Link Speeds & Practical Constraints)
* **非對稱速率組合：** 最常見為 Server 介面較慢（如 10G/25G），ISL 介面較快（如 40G/100G）。此舉能以更少的 Spine 數量提供相同的超賣比，大幅節省線纜與設備管理開銷。
* **實務物理限制：** 受限於機櫃供電與散熱（風冷極限約 45 KVA，一般設計為 10 KVA），單一 Rack 通常僅容納 20 或 40 台伺服器。
    *   *實務計算：* 40 台 10G 伺服器 (400G) 搭配 4 條 40G 上鏈 (160G)，實際超賣比為 **2.5:1**，對於中小型數據中心完全可接受。

**Leaf 與 Spine 之間的互連鏈路 (ISL, Inter-Switch Link) 應該採用與伺服器相同的速率，還是更高速率？**

* **非對稱速率架構（High-Speed Uplink + Lower-Speed Downlink）—— 業界主流做法**
  * **架構師設計取捨與優勢：**
    1. **大幅減少 Spine 交換器數量與線纜成本（Cabling Cost）：** 以 40 台 10GbE 伺服器（下鏈總頻寬 400G）為例，若上鏈採用 40GbE，僅需 **10 台** Spine 即可達到 1:1 無超賣；若上鏈也用 10GbE，則需要 **40 台** Spine。Spine 數量減少 4 倍，顯著降低機房拉線與設備管理開銷。
    2. **降低大流量長串流（Elephant Flows）碰撞壅塞：** 在 Clos 網路中，ECMP 是透過 5-Tuple 進行 Flow Hashing 分流。採用單條大頻寬上鏈（如 100G），能提供更寬裕的管線，降低少數巨量流量（Elephant Flow）擠在同一條小管線上導致的隨機掉包。
    3. **簡化維運管理：** 控制平面需管理的實體交換器總數顯著減少。

* **對稱速率架構（同速率 Uplink 與 Downlink）—— 極少數超大規模（Web-scale）業者做法**
  * **實作方式：** 利用高埠數交換器（如 32 埠 40GbE），透過 Breakout 線纜將 40G 埠拆分為多個 10G 埠使用。
  * **三大特殊效益：**
    1. **用低埠數晶片建構超大規模兩層 Clos：** 32 埠 40G 原本只能連 $32^2 / 2 = 512$ 台伺服器；拆成 108 埠 10G 後，可連接高達 $108^2 / 2 = 5,832$ 台伺服器。
    2. **最佳化負載平衡（Load Balancing）：** 下一跳 Spine 數量大幅增加（例如從 16 台增加到 54 台），流量分流更均勻，可有效消除流量偏極化（Traffic Polarization）。
    3. **更細粒度的故障域（Fine-Grained Failure Domain）：** 單條 ISL 鏈路中斷僅損失 $1/54$（約 1.85%）的頻寬，對整體網路幾乎無感。

理論公式算出 2-Tier Clos 可連 $n^2 / 2$ 台伺服器（例如 64 埠交換器可連 2,048 台），但現實中為何無法完美精準對應？歸納出以下實體與硬體限制：

* **1. 機櫃供電與散熱限制 (Power and Cooling Limits)**
  * **物理極限：** 一座 42U 機櫃理論上可裝 40 台 1U 伺服器，但一般資料中心機櫃供電設計約在 **10 KVA**，傳統空氣冷卻極限約為 **45 KVA**。
  * **伺服器密度：** 受限於散熱與功耗（尤其是加上 GPU 後），多數企業每個機櫃僅配置 **20 台或 40 台伺服器**，無法填滿所有 Switch 埠位。

* **2. 交換晶片埠數與機櫃伺服器數量的配置計算 (Switch Silicon vs. Rack Density Math)**
  * **案例 A：40 台 10G 伺服器/機櫃 ＋ 64 埠 10G Leaf 交換器**
    * 用掉 40 埠連接伺服器（下鏈 400G），剩餘 24 埠。
    * 若保留 20 埠做 10G 上鏈，超賣比（Oversubscription Ratio）為 $400:200 = \mathbf{2:1}$。
    * 若將 24 埠 10G 組合為 6 埠 40G，並僅使用 4 埠連至 4 台 Spine，上鏈頻寬為 $160G$，超賣比為 $400:160 = \mathbf{2.5:1}$（對於多數小型數據中心而言這是極佳且可接受的配置）。
  * **案例 B：20 台伺服器/機櫃 ＋ 100G 交換晶片**
    * 若採用 25G 伺服器介面，20 台伺服器僅需 $20 \times 25G = 500G$ 下鏈（只需 5 埠 100G）。即使 1:1 無超賣上鏈也只需 5 埠 100G，總共才用掉 10 個 100G 埠，會造成 32/64 埠 100G 交換晶片嚴重浪費。
    * **架構師解法：** 組織會改採**雙鏈路連接（Dual-attached / Active-Active）**，將伺服器介面擴展為 40 個，以充分利用 Leaf 晶片埠數。
  * **案例 C：96 台高密度微伺服器/機櫃 @ 25G**
    * 下鏈需 $96 \times 25G = 2,400G$（占 24 埠 100G），剩餘 8 埠 100G 做上鏈，超賣比為 $2400:800 = \mathbf{3:1}$（若只用 4 埠上鏈，超賣比則為 $\\mathbf{6:1}$）。

* **3. 交換晶片廠商的產品線切割 (Switch Silicon Segmentation)**
  * 商用晶片商（如 Broadcom）會針對 Leaf 與 Spine 推出不同定位的晶片：
    * **Leaf 晶片（如 Broadcom Trident 系列）：** 著重於支援多速率降速（Breakout）、靈活接存伺服器與邊緣控制。
    * **Spine 晶片（如 Broadcom Tomahawk 系列）：** 著重於極致的吞吐量、對稱高介面密度與高速轉發效能。


### 細粒度故障域 (Fine-Grained Failure Domain)
* **控制爆炸半徑 (Blast Radius)：** 具備多台 Spine（如 16 或 32 台）。當單一 Spine 或單條鏈路故障時，僅損失 $1/16$ 的總頻寬（相比傳統 Access-Agg 架構單點故障即損失 50% 頻寬）。
* **路由收斂隔離：** 路由協定會自動繞過故障鏈路，將故障衝擊嚴格限制於直連節點，不會引發全網坍塌。

## Clos 拓撲的橫向擴展：三層 Clos 拓撲 (Scaling the Clos Topology)

當伺服器規模超過單一 2-Tier Clos（如 2,048 台）時，可無縫擴展為 **3-Tier Clos 架構**：

* **計算數據證明：三層式 Clos 拓撲公式** (假設採用 $n$ 埠交換器，層間保持 1:1 超賣比)：[2-Tier 前提](#2-tier-前提)]
    * **可連接的最大伺服器總數：**
        $$\text{Max Servers} = \frac{n^3}{4}$$

        * *公式推導*：
            1. 在 3-Tier 架構中，每個單元（Pod）由 $\frac{n}{2}$ 台 Spine 與 $\frac{n}{2}$ 台 Leaf 組成。
            2. 每個 Pod 內部可容納的伺服器數 $= \frac{n}{2}\text{ (Leaf 數)} \times \frac{n}{2}\text{ (伺服器埠數)} = \frac{n^2}{4}$。
            3. 每台 Spine 的 $\frac{n}{2}$ 埠向下連 Leaf，另外 $\frac{n}{2}$ 埠向上連 Super-Spine。因此全網共有 $n$ 台 Super-Spine，可支援 $\frac{n}{2}$ 個 Pod。
            4. 全網總伺服器數 $= \frac{n}{2}\text{ (Pod 數量)} \times \frac{n^2}{4}\text{ (每個 Pod 的伺服器數)} = \mathbf{\frac{n^3}{4}}$。

        * *證明範例 (64 埠交換器)：* $64^3 / 4 = \mathbf{65,536}$ 台伺服器。
        * *證明範例 (128 埠交換器)：* $128^3 / 4 = \mathbf{524,288}$ 台伺服器。
    * **完全建構所需的交換器總數：**
        $$\text{Total Switches} = n + n^2$$
        * *公式推導*：
            1. **Super-Spine 層**：共 **$n$** 台交換器。
            2. **Pod 內部（Spine + Leaf）**：全網共有 $\frac{n}{2}$ 個 Pod，每個 Pod 內含有 $\frac{n}{2}\text{ Spine} + \frac{n}{2}\text{ Leaf} = n$ 台交換器。
            3. Pod 層交換器總數 $= \frac{n}{2}\text{ (Pod 數)} \times n = \frac{n^2}{2}$？不，若考慮全網等價交織，每個 Super-Spine 有 $n$ 個埠接向 $n$ 個 Spine 區域，整體 Pod 區域設備總量為 **$n^2$** 台（即 $n$ 個 Super-Spine $\times n$ 條下鏈）。
            4. 總交換器數 $= n\text{ (Super-Spine)} + n^2\text{ (Pod 內 Spine與Leaf總和)} = \mathbf{n + n^2}$。

        * *證明範例 (64 埠交換器)：* $64 + 64^2 = \mathbf{4,160}$ 台交換器。

* **兩種三層 Clos 架構模型對比 (Comparing the Two Three-Tier Models)：**[可先理解此章節](#3-tier-clos-的兩種架構規劃模型圖解)

| 比較維度 | 虛擬機箱模型 (Virtual Chassis Model) | Pod / 集群模型 (Pod / Cluster Model) |
| :--- | :--- | :--- |
| **代表業者** | Facebook（如 Backpack 設計） | Microsoft, Amazon 及多數大型網際網路業者 |
| **拓撲結構** | 將 2-Tier Clos 封裝於大機箱內作為 Crossbar，外部再接 Leaf | 將 2-Tier Clos 劃分為 Pod，上方新增 **Super-Spine** 層連接各 Pod |
| **延遲一致性** | **極度均勻**。任意兩台伺服器跨網傳輸均為 5 跳 (Hops)，延遲極致一致。 | **分階延遲**。Pod 內部傳輸為 3 跳，跨 Pod 傳輸為 5 跳。 |
| **增量擴建彈性** | 擴建門檻高。初始即需投資較多 Super-Spine/Spine 交換器，前端成本大。 | **極佳**。可先建構單一 Pod，隨流量增長再補充 Super-Spine，資金利用率高。 |

### 3-Tier Clos 的兩種架構規劃模型圖解


在實務建構 3-Tier Clos 時，業界主要存在兩種構建模型（以 4 埠交換器為例進行圖解）：

1. Pod / Cluster Model（Pod / 集群模型）
    * **架構概念**：將原本的 2-Tier Clos 打包為一個獨立的單元（Pod 或 Cluster），Spine 交換器的上鏈抽出一半的埠，向上連接至全新的 **Super-Spine** 層。
    * **代表業者**：Microsoft Azure、Amazon AWS 及多數大型雲端資料中心。
    * **ASCII 拓撲示意圖**：

    ```text
                    [ Super-Spine Layer ]
                    +----+        +----+
                    |SS1 |        |SS2 |  ... (共 n 台 Super-Spine)
                    +----+        +----+
                    /  \          /  \
            +---------+    +---+----+    +---------+
            |                  |                   |
    [ Pod 1 (Cluster 1) ]    |             [ Pod 2 (Cluster 2) ]
    +----+        +----+     |             +----+        +----+
    | S1 |        | S2 |     |             | S3 |        | S4 |  (Spine)
    +----+        +----+     |             +----+        +----+
     /  \          /  \      |              /  \          /  \
    +--+ +--+     +--+ +--+  |            +--+ +--+     +--+ +--+
    |L1| |L2|     |L3| |L4|  |            |L5| |L6|     |L7| |L8| (Leaf)
    +--+ +--+     +--+ +--+               +--+ +--+     +--+ +--+
    ||   ||       ||   ||                 ||   ||       ||   ||
    [Servers]     [Servers]               [Servers]     [Servers]
    ```

    * **規劃特點**：
        * **延遲非對稱**：Pod 內部通訊為 3 跳（HopCount = 3），跨 Pod 通訊需經過 Super-Spine，為 5 跳（HopCount = 5）。
        * **分階段擴建（Incremental Build Out）**：初期只需部署 1 個 Pod 與少量的 Super-Spine；隨著流量增長再逐步動態擴充 Pod 與 Super-Spine，**資金利用率極高**。

2. Virtual Chassis Model（虛擬機箱模型）
    * **架構概念**：不劃分 Pod，而是將 Spine 與 Super-Spine 封裝在一個邏輯大機箱內（如 Facebook Backpack），外部直接連接獨立的 Leaf 層。
    * **代表業者**：Facebook (Meta)。
    * **ASCII 拓撲示意圖**：

    ```text
                     [ Super-Spine Layer ]
                     +----+        +----+
                     |SS1 |        |SS2 |
                     +----+        +----+
                       |             |
           +-----------+-------------+-----------+
           |   [ Virtual Chassis / Backplane ]   |
           |   +----+                 +----+     |
           |   | S1 |                 | S2 |     | (Spine)
           |   +----+                 +----+     |
           +-----+-----------------------+-------+
                 |                       |
        +--------+--------+     +--------+--------+
        |                 |     |                 |
      +---+             +---+  +---+             +---+
      |T1 |             |T2 |  |T3 |             |T4 | (Top-of-Rack / Leaf)
      +---+             +---+  +---+             +---+
        ||                ||     ||                ||
    [Servers]         [Servers][Servers]       [Servers]
    ```

    * **規劃特點**：
        * **延遲高度一致**：任意兩台伺服器跨網傳輸均均勻為 5 跳，具備極佳的對稱性，非常適合運行單一巨型分散式應用（如搜尋引擎、MapReduce）。
        * **擴建門檻高**：初始建置即需部署完整的虛擬機箱內部結構，前期的資本支出（CapEx）較高。


### 2-Tier 前提

要理解 3-Tier 的擴展，必須先建立 2-Tier 的基本數學模型。 假設全網採用 $n$ 埠（$n$-port）相同速率的交換器，且下鏈（面向伺服器）與上鏈（面向 Spine）維持 1:1 無超賣比（Nonblocking / 1:1 Oversubscription）：


* **2-Tier 拓撲結構**：
    * 每台 Leaf 交換器使用 $\frac{n}{2}$ 埠連接伺服器，另外 $\frac{n}{2}$ 埠上鏈連接至所有 Spine。
    * 每台 Spine 交換器的 $n$ 個埠全部用於連接 Leaf 交換器（最多可連 $n$ 台 Leaf）。
* **最大支援伺服器總數公式**：
    $\text{Max Servers}_{\text{2-Tier}} = \frac{n^2}{2}$
    * *公式推導*：$n\text{ 台 Leaf} \times \frac{n}{2}\text{ (每台 Leaf 連接的伺服器埠數)} = \frac{n^2}{2}$。
* **總交換器需求量公式**：
    $\text{Total Switches}_{\text{2-Tier}} = n + \frac{n}{2}$
    * *公式推導*：$n\text{ 台 Leaf} + \frac{n}{2}\text{ 台 Spine} = \frac{3n}{2}$。

> [!TIP]
> 💡 **瓶頸說明**：對於大型雲端業者，單一 2-Tier Clos（即使採用 64 埠晶片）上限僅為 2,048 台伺服器，無法滿足超大規模需求，這正是引入 3-Tier Clos 的核心動機。

## Clos 拓撲對網路維運的深遠影響 (Implications of the Clos Topology)
1. **重新定義排錯與備料 (Rethinking Failures)：** 固定盒式設備故障型態簡單（Single silicon/CPU），維運改採「整台直接抽換 (Swap-out)」，將故障設備移至 Offline 環境除錯，不再於線上網路救援複雜機箱。
2. **實體線纜驗證 (Cabling Verification)：** 密集的 ISL 線纜需要自動化工具檢測。例如開源項目 **PTM (Prescriptive Topology Manager)** 或 Ansible Playbook，結合 LLDP 比對拓撲 DOT 檔，防止高達 30% 的人工接線錯誤。
3. **自動化成為剛性需求 (Network Automation)：** 面对數百台盒式交換器與龐大的 IP/ASN 配置，手動 CLI 配置宣告失效，必須採用 Ansible/Python 等基礎設施即程式碼 (IaC) 工具。

## Clos 網路的最佳實踐 (Best Practices for a Clos Network)
* **嚴禁在 Leaf-Spine 間簡單堆疊多條實體鏈路 (No Multiple Links / Port-Channels)：**
    * 若 Leaf 至 Spine 之間存在多條鏈路，當其中一條斷開時，路由協定（如 BGP/OSPF）無法正確告知下游節點該 Spine 的頻寬已折半，導致上游 Leaf 繼續向其發送 100% 流量，引發隱蔽的隨機丟包與效能下降。
    * 正解：* 保持節點間鏈路數一致（通常為 1 條），若需擴充頻寬，應**增加 Spine 節點數量**。
* **Spine 交換器保持純粹連接性 (Spines as Only a Connector)：**
    * 不可將部分 Spine 獨自連接外部邊界路由器 (Border Routers) 或安全設備，這會破壞流量對稱性並製造熱點 (Hotspots)。
* **慎用傳統大型機箱作為 Spine (Use of Chassis as Spine)：**
    * 傳統機箱具備複雜的內部控制板與背板，故障時形態複雜；除非採用 OCP 認證、內部背板即為純 Clos 拓撲的敞開式機箱，否則應優先使用固定盒式交換器。

## 主機連接模型 (Host Attach Models)
* **單鏈路連接 (Single-attached)：** 伺服器單網卡連接至單一 Leaf，架構極簡，大規模雲端業者主流採用。
* **雙鏈路連接 (Dual-attached)：** 企業數據中心常見（防止單一 Leaf 升級或故障導致 Rack 停機）。
    * 主動-被動模式 (Active-Standby)。
    * 主動-主動模式 (Active-Active / Bond)：主機側採用 LACP 綁定，交換器側需實施廠商專有的 **MLAG**（如 Cisco vPC、Cumulus CLAG、Arista MLAG），使主機誤以為連接至同一台邏輯交換器。

### 1. 單鏈路連接模式 (Single-Attached Host Model)

* **架構特性**：伺服器配備單張網路卡 (NIC)，僅連接至單一台 Leaf (ToR) 交換器。
* **系統設計考量**：
    * **優點**：極致簡化控制平面，無需複雜的 L2 跨機箱協定或堆疊；成本最低。
    * **適用場景**：超大規模雲端（Web-Scale）業者主流採用。此類架構將高可用性 (HA) 移至應用層（如 Kubernetes Pod 重建或微服務冗餘），容許單一 Rack 或 Leaf 故障。
* **ASCII 架構圖**：
```text
       [ Spine 1 ]       [ Spine 2 ]
            \                 /
             +---------------+
             |               |
        [ Leaf 1 ]       [ Leaf 2 ]
            |
            | (1x 10G/25G NIC)
            v
       [  Server  ]
```


### 雙上鏈 L2 綁定與傳統 MLAG 模式 (Dual-Attached with MLAG)

* **架構特性**：伺服器雙上鏈至兩台不同的 Leaf 交換器。
    * **主機側**：設定標準 IEEE 802.3ad 綁定 (Bonding / Port-Channel / LACP)。
    * **交換器側**：兩台 Leaf 執行廠商專有的 **MLAG** 協定（如 Cisco vPC、Cumulus CLAG、Arista MLAG），使主機誤以為連接至單一邏輯交換器。
    * **控制平面**：兩台 Leaf 之間必須透過一條專用的實體 **Peer-Link** 交換控制狀態與同步 MAC 位址。
* **ASCII 架構圖**：
```text
           [ Spine 1 ]       [ Spine 2 ]
                \                 /
                 +---------------+
                 |               |
            [ Leaf 1 ] <=======> [ Leaf 2 ]  <--- (實體 Peer-Link)
                \                 /
                 \               /
                  \ (802.3ad)   /
                   \   Bond    /
                    v         v
                [    Server    ]
```

### 雙上鏈 EVPN 無 Peer-Link 模式 (Dual-Attached EVPN MLAG)

* **架構特性**：結合網路虛擬化 Overlay 技術（如 EVPN VXLAN）。
    * **消除專用連線**：利用 EVPN 控制平面（RT-1 / RT-4 路由通告）自動同步主機可達性與多播保護（Designated Forwarder），**徹底省去傳統 MLAG 兩台 Leaf 之間的實體專用 Peer-Link**。
    * **主機側**：保持標準 802.3ad Bond，達到跨設備 Active-Active 雙活流量轉發。
* **ASCII 架構圖 (對應內文 Figure 2-7(b))**：
```text
           [ Spine 1 ]       [ Spine 2 ]
                \                 /
                 +---------------+
                 |               |
            [ Leaf 1 ]           [ Leaf 2 ]  <--- (無需實體 Peer-Link，
                \                 /               改由 EVPN/VXLAN 控制平面同步)
                 \               /
                  \ (802.3ad)   /
                   \   Bond    /
                    v         v
                [    Server    ]
```
### 主機直接路由模式 (Routing to the Host)

* **架構特性**：打破傳統 L2 邊界，將 L3 路由（IP Routing）直接推進至伺服器主機內部。
    * **主機側**：主機內部運行路由套件（如 FRR、Calico、Kube-router），分別與兩台 Leaf 建立 **BGP / OSPF 鄰居關係**。
    * **流量負載**：利用 **ECMP (等價多路徑路由)** 進行雙上鏈流量分流，不再需要 L2 綁定（Bond）或 MLAG 等複雜機制。
* **ASCII 架構圖**：
```text
           [ Spine 1 ]       [ Spine 2 ]
                \                 /
                 +---------------+
                 |               |
            [ Leaf 1 ]           [ Leaf 2 ]
                ^                 ^
                 \ (L3 Peering / / (L3 Peering / ECMP)
                  \  BGP/FRR)   /
                   \           /
                [    Server    ]
```
