
# Network Observability（網路可觀測性）

* **分散式系統的痛點**：引述 Charity Majors（"最髒的秘密是許多故障從未真正被解釋或理解..."）與 Leslie Lamport（"分散式系統就是當你甚至不知道存在的電腦故障時，會讓你自己的電腦無法使用..."）的名言。
* **網路工程師的清白 (Mean Time to Innocence)**：當微服務應用發生延遲或中斷時，網路往往首當其衝被質疑（"Is it the network?"）。**可觀測性（Observability）與自動化（Automation）並列為雲端原生資料中心運育現代基礎設施的兩大核心支柱**。

## 何謂可觀測性？ (What Is Observability?)

* **Monitoring（監控）vs. Observability（可觀測性）的本質差異**：
  * **監控 (Monitoring)**：回答**「系統是否正常運作？ (Is the system working?)」**，捕捉**「已知 (Known Knowns)」**。例如：監控 BGP Session 是否處於 Established 狀態。
  * **可觀測性 (Observability)**：回答**「為什麼系統運作不正常？ (Why is it not working?)」**，追蹤**「未知 (Unknown Unknowns)」**。允許工程師透過系統輸出的外部資料（Outputs），推導內部未知的異常根因。
* **Twitter 對可觀測性的定義**：整合指標 (Metrics)、日誌 (Logs)、分散式呼叫追蹤 (Distributed Traces) 與可搜尋的日誌索引，支援服務健康度監控與根因調查。
* **簡化維運認知負擔**：
  * 當全網存在 128 個 BGP Session 時，傳統命令列印出全量狀態極難人工排查；**高可觀測性系統應能精準僅回傳「失敗的 Session 及其失敗原因」**。


## 網路可觀測性的現狀與困境 (The Current State of Network Observability)

#### 1. SNMP 的幻滅 (The Disenchantments of SNMP)
* **歷史包袱**：誕生於 1980 年代末，基於 MIB (Management Information Base) 與 OID (Object ID) 樹狀結構，採用 ASN.1 進行二進位編碼。
* **Pull 模式 (拉取模型) 的效能瓶頸**：
  * 由 NMS (Network Management System) 定期發起 MIB Walk。在大型路由器上頻繁輪詢會推高 CPU 負載甚至導致系統崩潰，因此監控間隔通常被迫拉長至 **1 到 5 分鐘**。
* **時間顆粒度失真 (Time Resolution Mismatch)**：
  * 伺服器/容器端收集 1 秒或 15 秒級指標，而網路交換器僅收集 1~5 分鐘級指標。**瞬間的網路微抖動（Latency Spikes、Drop）在 SNMP 統計中被平均化平滑消除**，引發應用團隊與網路團隊之間的責任推諉。
* **缺少現代 Data Model**：許多 CLI 具備的關鍵 Debug 資訊，完全沒有對應的標準 SNMP MIB。

#### 2. 逐台設備排查法 (Box-by-Box Approach)
* **傳統除錯模式**：工程師透過 SSH 登入多台設備、開啟多個視窗，利用 `ping` 與 `traceroute` 逐台對比路由表與協定狀態（例如排查 OSPF 鄰居無法建立，發現是兩端 MTU 不匹配）。此模式在大規模 Clos 拓撲中完全無法擴展。

## 為什麼網路可觀測性如此困難？ (Why Is Observability Difficult with Networking?)

* **專有設備 (Appliance) vs. 通用平台 (Platform)**：
  * 計算伺服器是開放平台，可自由安裝 `statsd`、`collectd`、`Prometheus`；傳統交換器是封閉器具，資料收集與傳輸機制無法解耦。
* **交換晶片 (Packet-Switching Silicon) 的不透明性**：
  * 伺服器軟體可以進行單步執行 (Single-Step Debugging)；但高速交換晶片硬體無法單步偵測。雖然新一代可程式化晶片（如 **Barefoot Tofino**）開始提供晶片級封包追蹤，但分析工具鏈仍處於演進階段。

## 資料中心網路可觀測性的特殊挑戰與契機 (Special Characteristics)

* **四大特殊挑戰 (Challenges)**：
  1. **多路徑 (Multipathing / ECMP)**：Clos 拓撲中多路徑為常態。標準 `ping` 僅測試單一路徑；傳統 `traceroute` 不支援多路徑（Ubuntu 須加 `-u` 參數，或使用 `mtr`）。
  2. **容器與微服務 (Containers & Microservices)**：端點極度短暫 (Ephemeral)，傳統工具缺乏容器與實體 IP 的映射，難以進行事後剖析 (Post-mortem Analysis)。
  3. **自動化 (Automation)**：自動化程式碼若有 Bug，影響會瞬時擴散至全網。
  4. **固定規格交換器 (Fixed-Form-Factor Switches)**：設備台數暴增，傳統 Box-by-Box 排查徹底失效。
* **兩大雲端原生契機 (Advantages)**：
  1. **盒式設備小而同質**：單台設備狀態資料量少，允許更高頻率的輪詢與統一 Telemetry 部署。
  2. **網路解耦 (Network Disaggregation)**：交換器運行 Linux OS，可統一 Linux 維運工具鏈，促進**串流遙測 (Streaming Telemetry)** 的普及。


## 可觀測性的解構與遙測機制 (Decomposing Observability & Telemetry)

#### 1. 遙測收集什麼？ (What Do We Gather?)
* **指標 (Metrics)、日誌 (Logs) 與封包追蹤 (Packet Tracing/sFlow)**。
* **兩大收集哲學**：
  * *Etsy 模式*：`Church of Graphs`（只要會動的就監控）。
  * *Charity Majors & Brendan Gregg 模式*：**USE 模型 (Utilization, Saturation, Errors)**：
    * **U (Utilization / 使用率)**：介面收發封包數與流量 (Bytes)。
    * **S (Saturation / 飽和度)**：Buffer 緩衝區佔用率。
    * **E (Errors / 錯誤率)**：Drop 丟包與 Error 統計。
* **偏極化比率 (Polarization Ratio)**：
  * Clos 拓撲中 Leaf 上鏈頻寬利用率是否平衡。若偏離 1，代表 Flow Hashing 產生 Elephant Flow 擁塞，需微調 Hashing Seed。
* **Google SRE 金指標**：延遲 (Latency)。

#### 2. 遙測如何收集？ (How Do We Gather?)
* **串流遙測 (Streaming Telemetry)**：利用 Prometheus、InfluxDB、Kafka 進行資料串流；日誌由 Syslog 送往 ELK (Elasticsearch, Logstash, Kibana) 或 Splunk。
* **Push (推) vs. Pull (拉) 深度對比**：
  * **Push 模式 (推)**：Agent 在事件發生時（如鏈路斷開）即時推送，可捕捉系統潰散前最後的臨終訊息；但需要在 NOS 上安裝專屬 Agent。
  * **Pull 模式 (拉 - 如 Prometheus)**：中央 Collector 定期輪詢。可直接利用原生 REST API 或 SNMP，無需修改 Agent；但極端故障時可能因輪詢未到而遺失事件。
  * **SNMP 的妥協方案**：採 Pull 模式收集一般統計，並採 Push 模式 (SNMP Traps) 處理極重要告警。

#### 3. 遙測何時收集與儲存？ (When & Storing the Data)
* **時間顆粒度**：推薦計算端與網路端統一採用 **15 秒 (15-second interval)** 收集週期（Prometheus 預設值）。
* **拒絕數據歸納 (No Roll-ups)**：過去因儲存昂貴，會將每小時資料壓縮歸納為平均值，導致瞬間峰值消失。現代數據中心儲存廉價，**建議保留至少數天至數週的 15 秒原始細粒度資料 (Raw Data)**。

## 多重資料源、告警與儀表板 (Data Sources, Alerts & Dashboards)

* **故障型態與資料源對映**：
  * **完全連通失敗 (Failed Communication)**：檢視路由表、MAC 表、ARP/ND 表與 BGP 狀態。
  * **效能次優 (Suboptimal / Slow / Lossy)**：檢視介面使用率、Buffer 飽和度、Drops、sFlow 採樣與路由環路。
* **告警 (Alerting) 困境與告警疲勞 (Alert Fatigue)**：
  * CPU 瞬間 Spike 即發告警會導致工程師麻木忽略（狼來了效應）。應引入**持續多個週期的異常判定 (Anomaly over cycles)** 以減少偽陽性。
* **儀表板 (Dashboards) 的局限性**：
  * 引用 Charity Majors 名言：**「你無法透過儀表板來進行排錯 (You cannot debug with a dashboard)」**。
  * 儀表板（如 Grafana、Plotly）僅能呈現「問題存在」，無法精確指引「根因為何」。
* **未來解答：Ad-hoc 隨機查詢平台**：
  * 結合 Python `pandas` 或 SQL 語言，允許工程師像使用 Debugger 一樣，針對 TSDB 進行跨維度的關聯性隨機查詢。

**總結**：
可觀測性的本質是**「擺脫黑盒摸黑排查，建立具備高時間解析度 (15s) 與全網關聯性的數據透明度」**。透過採用 Linux 網路解耦、串流遙測 (Streaming Telemetry) 與 USE 模型，網路團隊得以與計算/容器團隊站在相同的時間維度上，精確定位雲端原生資料中心的未知異常。
