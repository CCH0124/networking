# Rethinking Network Design（重新思考網路設計）

* **核心宗旨**：雲端原生資料中心網路（Cloud Native Data Center Network）不論規模大小（從 20~50 台交換器到 Hyperscaler 超大規模機房），其共同目標皆為**可靠性（Reliability）**與**營運成本效益（Operational Cost Efficiency）**。
* **三大顛覆性的設計原則**：
  1. **標準且簡單的構建塊 (Standard, simple building blocks)**
  2. **重新思考網路故障 (A reconsideration of network failures)**
  3. **對簡潔與精簡主義的極致追求 (Ruthless focus on simplicity / The Pursuit of Less)**

---

### 標準且簡單的構建塊 (Standard, Simple Building Blocks)

* **極簡的硬體品項 (Minimal SKUs)**：利用 Clos 拓撲與網路解耦，全網只需 1~2 種固定規格（Fixed-form-factor）交換器（例如 Leaf 交換器配置 48x25GbE + 8x100GbE；Spine 交換器配置 32~128x100GbE）即可彈性擴充至任意規模。
* **摒棄傳統大機箱 (Avoid Traditional Large Chassis)**：傳統大型機箱（Chassis）交換器內部含有專有 ASIC、雙控制卡與複雜過渡匯流排，維運與故障排查極為困難。
* **新型 OCP 內部 Clos 機箱 (OCP-Approved Chassis)**：若為了減少線纜採購，可以採用 Facebook OCP 規範的機箱（如 Minipack/Backpack）。其背板本質上就是由商用晶片（Merchant Silicon）組成的內部 Clos 網路，且每個 Linecard 獨立運作，沒有中央控制處理器的單點瓶頸。
* **網路解耦 (Network Disaggregation)**：
  * **作業系統統一，硬體供應商多元**：解耦允許企業選用統一的 NOS（如 Linux / Cumulus Linux），同時向不同 ODM/OEM 廠商（如 Dell、Edgecore）採購硬體，既能分散供應鏈風險、避免廠商鎖定（Vendor Lock-in），又保留了統一的 Linux 維運介面。

### 重新思考網路故障：見樹不見林 (Failure: Missing the Forest for the Trees)
* **回歸 IP 原生容錯模型**：網路設計不應追求「單一節點永不故障」，而應假設「個別組件必會故障（Components will fail）」，並利用小型構建塊提供的自然冗餘性確保全網持續運作。
* **控制爆炸半徑 (Blast Radius)**：
  * 小型固定規格交換器能將故障影響限制在極小範圍。
  * 若採用 512 埠的大型 Spine 機箱，一旦發生故障，爆炸半徑將擴大至整個 Pod 甚至全網。拆分為三層 Clos（如 8 個 Pod、每 Pod 64 Rack）能提供更高的可靠性。
* **L2 故障模型 vs. L3 故障模型 (L2 Failure Model Versus L3 Failure Model)**：
  * **L2 (STP) 故障開放（Fail Open/Promiscuous）**：當 STP 定時器逾時，埠會誤以為對方死掉而轉為轉發狀態，進而產生二層環路與廣播風暴，導致全網癱瘓。
  * **L3 故障關閉（Fail Closed）**：當 L3 路由器在死鎖時間內未收到鄰居 Hello，直接標註鄰居死亡並自路由表中移除，其他節點自動繞道，不引發全網連鎖崩潰。
* **簡單故障 vs. 複雜故障 (Simple Versus Complex Failures)**：
  * 單晶片、單 CPU 的盒式交換器故障型態極為簡單，故障時直接線上手動「熱抽換（Swap-out）」並至線下排查，大幅縮短 MTTR。
* **處理升級與維護 (Handling Upgrades)**：
  * **摒棄 ISSU 迷思**：傳統廠商宣傳的在線軟體升級（ISSU, In-Service Software Upgrade）在實務中極度不可靠，常引發高優先級 Bug 且拖慢版本釋出。
  * **L3 流量排水（Graceful Drain）**：雲端原生資料中心全面棄用 ISSU，改利用 L3 路由協定（如 OSPF max-metric / BGP AS_PATH prepend / Graceful Shutdown）先將流量優雅引離該節點，隨後重載（Reload）並完成升級。

> [!NOTE]
> 展示了前 Cisco 技術行銷總監 Joe Onisick 的推文（Tweet）截圖。推文內文寫道：
> *“ISSU is a lie. Drain, reload, re-add. Anything else is a recipe for tears and late night phone calls.”*
> （ISSU 是一個謊言。正確做法是流量排水、重載、重新加入。其他任何做法都是眼淚與深夜緊急電話的配方。）

### 對簡潔與精簡主義的極致追求 (The Pursuit of Less)
* **反思功能貪婪（Gordon Gekko vs. Marissa Mayer 哲學）**：
  * 傳統網路工程師受「功能越多越好（Greed is good）」心態影響，要求包含長串無用功能的 RFI/RFP 需求清單。
  * 雲端原生運算採行 Marissa Mayer 哲學：「在需要的時間提供需要的功能，而非提供所有可能用到的東西（What you want, when you want it. As opposed to everything you could ever want, even when you don't.）」。
* **正確架構的作用 (How the Right Architecture Helps)**：
  * 全面採用純 L3 Clos 拓撲後，傳統 L2 所需的複雜修補協定（STP、LACP、FHRP、UDLD、VLAN 擴充）被徹底消除。
  * 整個數據中心 Fabric 簡化至僅需 **一個路由協定 (Routing Protocol) + BFD (微秒檢測)** 即可穩定運作。
* **功能集精簡主義 (Feature Set Essentialism)**：
  * 引用 Greg McKeown《精簡主義》(Essentialism) 的核心概念：*Weniger aber besser*（Less, but better，更少但更好）。
  * 盡可能減少配置中的調節參數（Knobs）。例如：優先選用 **Unnumbered Interfaces**（無 IP 介面）、**單一 eBGP 會話承載 Overlay/Underlay**，以及用**頭端複製 (Head-end Replication)** 替代複雜的 IP 多播。

### 雲端原生網路設計原則的現實限制 (Constraints on the Cloud Native Network Design Principles)

* **應用程式的歷史包袱 (Legacy Application Constraints)**：公有雲業者可以從零開始設計不支援 L2 廣播/多播的 VPC；但企業資料中心常繼承依賴 L2 廣播/多播叢集發現的舊型應用（Legacy Apps）。
* **應對策略**：
  * 透過內部計費（Internal Chargeback）提高舊型網路的使用成本，誘導應用開發團隊將應用重構為 Cloud Native 微服務。
  * 將舊應用隔離至特定的舊型網路區域，防止其破壞核心 Clos Fabric 的極簡原則。
* **舊硬體資產限制**：在既有資產未折舊完成前，需採取漸進式替換。

### 雲端原生網路 vs. 傳統 Access-Agg 網路設計對比總結

#### 架構設計對比：

| 評估維度 | 雲端原生網路 (Cloud Native Networks) | 傳統 Access-Aggregation 網路 |
| :--- | :--- | :--- |
| **構建模塊 (Building Blocks)** | **標準、簡單且少樣化的盒式交換器** | 廠商專有、高複雜度的巨型機箱 (Chassis) |
| **可靠性來源 (Reliability Model)** | **依靠網路拓撲的自然冗餘，允許單點故障** | 依靠打造「永不故障」的單一昂貴高階節點 |
| **功能集 (Feature Set)** | **精簡主義 (Essential Set, *Weniger aber besser*)** | 龐大、複雜且充滿廠商特有擴充的功能清單 |
| **故障傳播 (Failure Domain)** | **L3 故障關閉 (Fail Closed)，爆炸半徑極小** | L2 故障開放 (Fail Open)，易引發廣播風暴全網癱瘓 |
| **軟體升級 (Software Upgrades)** | **L3 路由流量排水 (Drain) + 節點重載** | 依賴不可靠的在線升級 (ISSU) |
